# История диагностики и изменений OsaiTransfer

## 2026-11-25 (вечер) — Смешанная кодировка WinCE, Drag & Drop, сортировка и контекстное меню

### Исправлено
- **Диагностика и исправление пустой правой панели / ошибки `Not enough data. Body decoding failed` (`0x2D` / `0xC000003A`)**:
  - Установлено, что на контроллере OSAI (WinCE) одновременно присутствуют каталоги и файлы в настоящем Unicode UTF-16LE (например, `/PROGRAMS/В РАБОТУ`, 295 файлов) и в устаревшем CP1251-в-Latin-1 (например, `/PROGRAMS/WORK/338 фанера 20`, 12 файлов).
  - Прежний `encode_smb_name` принудительно перекодировал любую кириллицу в CP1251-в-Latin-1, из-за чего путь `/PROGRAMS/В РАБОТУ` искажался: перечисление возвращало пустоту, а `ComOpenAndx` при загрузке файла возвращал `STATUS_OBJECT_PATH_NOT_FOUND` (`0xC000003A`) с усечённым пакетом длиной 38 байт (`ByteCount = 15`), вызывавшим `ProtocolError` в `pysmb` и отравление буфера соединения для последующих запросов.
  - В `smb_client.py` убрано слепое перекодирование и реализовано посегментное разрешение путей `resolve_remote_path()` с сопоставлением точного `raw_name` и декодированного имени. Новые файлы и папки создаются в стандартном UTF-16LE; перезапись существующих CP1251-файлов сохраняет их `raw_name`.
  - При `ProtocolError` соединение `self._conn` принудительно сбрасывается (`disconnect()`), код NTSTATUS расшифровывается в понятное сообщение, добавлен однократный переконнект при обрыве сокета.
- **Передача и навигация (`app.py`)**:
  - Навигация, загрузка, скачивание и удаление используют `current_remote_raw_path` и `raw_name` (через `posixpath`).
  - Добавлена понятная подсказка при попытке открыть заблокированный Win32 58 сетевой диск через `.lnk`.
- **Сортировка по столбцам**:
  - Добавлена сортировка по заголовкам `Имя файла / папки`, `Размер`, `Дата изменения` с индикаторами `▲`/`▼` в обеих панелях (`..` всегда закреплена сверху, папки перед файлами, для папок также отображается дата изменения).
- **Drag & Drop**:
  - Реализован внутренний Drag & Drop между левой и правой панелями (загрузка на ЧПУ и скачивание на ПК с плавающей подсказкой), сохранён внешний Drag & Drop из Проводника (`tkinterdnd2`).
- **Системное контекстное меню Windows и просмотр файлов**:
  - На левой панели по ПКМ открывается нативное системное меню Windows (`IContextMenu`: *Открыть*, *Открыть с помощью*, *Печать*, *Свойства* и др.) с добавленными сверху пунктами `Загрузить на ЧПУ ➔` и `Быстрый просмотр текста`.
  - На правой панели (ЧПУ) по ПКМ добавлены: `👁 Открыть в программе Windows` (скачивание во временный кэш `%TEMP%\OsaiTransferPreview` через Userspace SMB1 и запуск штатным приложением Windows для `.bmp`, `.pdf`, УП), `📄 Быстрый просмотр текста (УП)` (встроенный просмотрщик с автоопределением UTF-8 / CP1251) и `🪟 Системное меню Windows...` для временной копии файла со станка.
- **Скрипты сборки (`build_remote.cmd`, `build.bat`)**:
  - Добавлены скрытые импорты `win32com.shell`, `win32gui`, `win32gui_struct`, `win32con`.
  - В `build_remote.cmd` существующий `config.ini` на Рабочем столе больше не перезаписывается при пересборке.

## 2026-11-19 — Отладка OsaiTransfer v1 на станке: диагностика 6 багов

Первый запуск на реальном станке выявил 6 проблем, разобранных и перенесённых в архитектуру `smb_client.py` и `config.ini`:
1. **Кириллица в устаревших каталогах (`/PROGRAMS/WORK`)**: часть записей WinCE содержала байты CP1251, декодированные как Latin-1; добавлена функция `decode_smb_name()`.
2. **Удаление файла с ЧПУ**: `conn.deleteFiles()` в `pysmb` вызывал дополнительный `listPath` и падал с `0xC000003A`. Переведено на прямой `SMBMessage(ComDeleteRequest(..., search_attributes=0x16))` с обязательным ведущим `\`.
3. **Создание и удаление папок**: реализованы прямые `ComCreateDirectoryRequest` / `ComDeleteDirectoryRequest` с ведущим `\`, а также рекурсивная загрузка/удаление/скачивание каталогов.
4. **Ярлыки `.lnk` на рабочем столе оператора**: добавлена зависимость `pywin32` для разрешения ярлыков на сетевые ресурсы.
5. **Формат УП `.anc`**: расширение `.anc` добавлено в `config.ini` и фильтр приложения.
6. **Drag & Drop**: добавлена зависимость `tkinterdnd2` (`TkinterDnD.Tk()`).

## 2026-11-06 — 2026-11-11 — Исследование сбоя SMB1 после обновления Windows 11

- **Сетевое окружение**: ПК оператора Windows 11 Pro 25H2 (`192.168.2.96` / шина станка `192.168.0.100`), контроллер OSAI COMPACT (`192.168.0.2`, Windows CE, SMB 1.0 Dialect 1.5, порты TCP 445 и 139, ресурсы `USER` и `OEM`).
- **Двусторонний захват `pktmon` (11.11.2026)**:
  - Опровергнута гипотеза о запросе уровня `0x106`: Windows 11 запрашивает штатный `TRANS2_FIND_FIRST2` (`InformationLevel = 0x0104`, `SMB_FIND_FILE_BOTH_DIRECTORY_INFO`).
  - Контроллер отвечает `STATUS_SUCCESS` (`0x00000000`), но в каждой записи поле `FileNameLength` включает завершающий 2-байтовый терминатор UTF-16 NUL (`\0\0`).
  - Смена транспорта TCP 445 → NetBT 139 проблему перечисления в Windows 11 не устранила; чтение известного файла по точному пути продолжало работать.
- **Проверка альтернатив**: kernel CIFS в современной Linux VM не прошёл согласование авторизации с WinCE (`sec=none` / `ntlm` / `ntlmv2`), что окончательно подтвердило выбор самостоятельного Userspace SMB1-клиента.
